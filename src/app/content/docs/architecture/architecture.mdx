## 1. High-Level System Architecture

This project is built using the Next.js framework, leveraging its capabilities for both frontend rendering and backend API routes. The application's architecture is broadly categorized into:

- **Frontend (UI/UX):** Developed with React.js components and Next.js for server-side rendering (SSR) and static site generation (SSG) where appropriate, ensuring a fast and responsive user experience.
- **Backend (API Routes):** Implemented using Next.js API routes (`src/app/api/**/*.ts`), serving as the interface for client-side requests and handling business logic. These routes interact with external services and the database.
- **Database:** Supabase serves as the primary data store, offering a PostgreSQL database, authentication services, and real-time capabilities. This choice provides a robust and scalable backend foundation.
- **Authentication:** Managed via NextAuth.js, integrated with GitHub OAuth for secure user registration and sign-in.
- **Content Management:** Markdown (`.mdx`) files are used for documentation and blog content, providing a flexible and developer-friendly way to manage static content.

The core principle behind this architecture is a modular, scalable, and secure application that can evolve efficiently.

## 2. Authentication and Authorization

This section details the implementation of user registration and sign-in, including API endpoints, the authentication flow, and data models.

### 2.1 API Endpoints

- **/api/register**: This endpoint initiates the user registration process by redirecting to the configured OAuth provider (GitHub). It acts as a gateway to the external authentication service.
- **/api/sign-in**: Similar to registration, this endpoint facilitates user sign-in by redirecting to the GitHub OAuth provider.
- **/api/auth/[...nextauth]**: This is the dynamic catch-all route managed by NextAuth.js. It handles all authentication-related callbacks (e.g., OAuth redirects), session management, and user data persistence with the database.

### 2.2 Authentication Flow

1.  **User Initiation**: A user attempts to register or sign in by navigating to `/api/register` or `/api/sign-in` (or clicking a respective UI button).
2.  **OAuth Redirection**: The application redirects the user to the GitHub OAuth provider's authorization page. This offloads authentication to a trusted external service.
3.  **GitHub Authentication**: The user authenticates directly with GitHub, granting permission for the application to access their profile information.
4.  **Authorization Code Callback**: GitHub redirects the user back to the application's NextAuth.js callback URL (e.g., `/api/auth/callback/github`) with an authorization code.
5.  **Token Exchange & Profile Retrieval**: NextAuth.js intercepts this callback, exchanges the authorization code for an access token with GitHub, and retrieves the user's profile information (e.g., email, name, image).
6.  **User Synchronization (Database)**: NextAuth.js interacts with the Supabase adapter (`@next-auth/supabase-adapter`) to check for an existing user. If the user does not exist, a new user record is created in the database.
7.  **Session Creation**: A secure session is established for the authenticated user, typically stored as a cookie.
8.  **Application Redirection**: The user is finally redirected to the main application, now authenticated and ready to access protected content.

### 2.3 GitHub OAuth Integration

The application leverages [NextAuth.js](https://next-auth.js.org/) for a streamlined and secure GitHub OAuth implementation. NextAuth.js simplifies the complex aspects of authentication, including token management, session handling, and adapter integration with various databases.

Configuration involves setting up a GitHub OAuth application to obtain client ID and secret, which are then provided to NextAuth.js. The callback URL must be precisely configured to `https://your-app-domain.com/api/auth/[...nextauth]`.

### 2.4 Data Models

The `User` model is central to authentication and user management:

- **User**: Represents an authenticated user within the system. The definition, including key properties like email, name, and role, is found in [`src/lib/models/user.ts`](src/lib/models/user.ts).

  ```typescript
  export interface User {
    email: string;
    name?: string;
    image?: string;
    emailVerified?: Date;
    role: 'user' | 'admin'; // Role-based access control (RBAC) is implemented
    createdAt: Date;
    updatedAt: Date;
  }
  ```

  _Insight:_ The `role` field is crucial for implementing role-based access control (RBAC), allowing different levels of permissions within the application (e.g., 'user' for general access, 'admin' for administrative functions).

### 2.5 Database Schema

Supabase (PostgreSQL) is the chosen database. The `users` table is fundamental for storing user authentication and profile data, seamlessly integrated via the `@next-auth/supabase-adapter`.

```sql
-- Example users table schema
-- This schema aligns with NextAuth.js's default user model expectations
CREATE TABLE users (
  id UUID PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL,
  name VARCHAR(255),
  image VARCHAR(255),
  emailVerified TIMESTAMPTZ,
  role VARCHAR(255) DEFAULT 'user',
  createdAt TIMESTAMPTZ DEFAULT NOW(),
  updatedAt TIMESTAMPTZ DEFAULT NOW()
);
```

_Insight:_ Using `UUID` for `id` provides globally unique identifiers, which is a good practice for distributed systems or when merging data from different sources. The `DEFAULT NOW()` for `createdAt` and `updatedAt` simplifies timestamp management.

## 3. Middleware and Public Path Management

The application employs a robust middleware (`src/middleware.ts`) for centralized authentication and authorization checks.

### 3.1 Role of Middleware

The middleware acts as a gatekeeper, intercepting requests before they reach Next.js pages or API routes. Its primary responsibilities include:

- **Authentication Check**: Verifying the presence and validity of an authentication token (session).
- **Authorization**: Ensuring that authenticated users have the necessary permissions (e.g., based on their `role`) to access specific resources.
- **Redirection**: Redirecting unauthenticated or unauthorized users to designated pages (e.g., sign-in or a 403 Forbidden page).

### 3.2 Public Paths Configuration

A crucial aspect of the middleware's functionality is the identification of "public paths" — routes that do not require authentication. These paths are explicitly defined in [`src/config/publicPaths.ts`](src/config/publicPaths.ts). This centralized configuration promotes:

- **Maintainability**: Easily add or remove public routes without modifying core middleware logic.
- **Security**: Prevents accidental exposure of protected routes.
- **Clarity**: Provides a clear overview of publicly accessible endpoints.

### 3.3 Implementation Details

- **Token Retrieval**: The `middleware.ts` file utilizes the `getToken` function from `next-auth/jwt` to securely retrieve and parse the JSON Web Token (JWT) from the request. This token contains the user's session information.
- **Path Matching**: The `publicPaths.ts` file exports an array containing string patterns and regular expressions (`RegExp`) to flexibly define which routes are exempt from authentication checks. The middleware iteratively matches incoming request URLs against these patterns.

- **Data Flow Diagram**: Illustrating how data moves through the system, from user input, through API routes, to the database, and back to the user interface.
